# 📄 Product Requirements Document: FloodPulse (Nairobi)
**Project Code:** FP-NBO-2026

## 1. Problem Statement
Existing navigation tools in Nairobi rely on static road data and active internet. During flash floods in the Mbagathi basin, infrastructure fails rapidly. Users lack a real-time, offline-first tool to identify "Ground Truth" hazards and find high-ground ridges.

## 2. Goals & Objectives
- **Goal:** Reduce transit-related flood fatalities by 50% in pilot areas.
- **Objective:** Deploy a multimodal agentic pipeline capable of identifying flood boundaries and safe transit paths.
- **Strategic Metric:** Maintain high-fidelity spatial reasoning via `Gemini 2.5/3.5 Flash & Flash-Lite` and orchestrate reliable navigation directives through modular, ADK-driven sequential agentic pipelines.

## 3. System Architecture
FloodPulse utilizes a Modular Agentic Simulation pattern, evolving from static identity creation (Level 0) into a real-time Production Studio (Level 1) for agentic assets.

- **Level 0 (The Gallery):** A persistent registry for personas (Sarah, Juma, Kamau) and finalized mission assets.
- **Level 1 (The Studio):** The core Agentic Synthesis engine. It uses the **Google Agent Development Kit (ADK)** to orchestrate specialized sub-agents (Vision Analyst, Weather Gatherer) through a sequential delegation loop, ensuring atomic state management and session-scoped reliability. The core engine utilizes an Agentic Resilience Layer (`utils.py` and `genai_retry` logic) to manage API fluctuations and quota constraints. State is managed through an explicit **Context-Setter Pattern**, requiring the Orchestrator to validate and persist mission parameters before task delegation.
- **The Sandbox (Lab/Validation):** An isolated, ephemeral environment used for Model Context Protocol (MCP) tool-calling validation, ADC-based authentication testing, and diagnostic reporting.
- **Level 2 Graph Orchestration:** Google Cloud Spanner backbone for persistent node-based navigation.
- **Level 3 (Autonomous Emergency Operations):** Fully autonomous multi-agent orchestration and dispatch powered by Spanner transactional integrity, strict role separation (Risk Analyst vs. Mission Operations), and graph-based rescue routing

## 4. Technical Specifications
### 4.1 Level 0: The Gallery
- Model: Gemini 3.1 Flash Image (Nano Banana 2).
- Logic: Implemented `create_identity.py` and `generator.py` using an Orchestrator/Worker pattern.
- Output: Consistent visual assets stored in `level_0/outputs/.`


### 4.2 Level 1: The Studio 
- **FR1 (Sequential Orchestration):** The `FloodPulseStudio` uses `SequentialAgent` logic to map user intent to a precise, context-aware execution flow.
- **FR2 (Telemetry-Aware Synthesis):** The orchestrator pulls real-time environmental telemetry (Weather) and terrain data (Vision) to generate a unified mission risk assessment.
- **FR3 (Artifact Promotion):** Automated pipeline moves validated assets from /level_0/outputs to the public `/level_1/assets` registry.
- **FR4 (Memory Injection):** Contextual injection of persona metadata (Level 0) into `callback_context` to ensure agents are "Persona-Aware."
- **FR5 (Interaction):** Interactive discovery phase where the root agent greets the user and determines mission parameters before synthesizing assets.
- **FR6 (Idempotency):** The ADK `InMemorySessionService` tracks invocation_ids to ensure atomic tool execution and cost-efficient API usage.
- **FR7 (Resilience Integration):** All external tool calls are wrapped in `http/gen_ai_retry` (exponential backoff with jitter) to mitigate `429 RESOURCE_EXHAUSTED` and `503 UNAVAILABLE errors`.
- **FR8 (Context-Setter Gatekeeper):** The Orchestrator forces an `update_mission_context` execution for every session, transforming raw user input into a persistent `session.state` that fuels downstream domain sub-agents.
- **FR9 (Root-Level Utility Infrastructure):** Migration of shared utility logic to the root `/utils.py` module to ensure consistent package namespace resolution and eliminate `ImportError` regressions.

### 4.3 The Sandbox 
- **Purpose:** To serve as an independent validation layer for post-mission audit and high-fidelity quality control.
- **FR10 (Audit Verification):** The Sandbox acts as an independent auditor; tools must be verified to function within the post-execution pipeline, validating assets generated by Level 1 (Studio) against mission baselines.
- **FR11 (Dual-Mode Authentication):** All tools must support both **Application Default Credentials (ADC)** for enterprise-grade production and **API Keys** for rapid local prototyping, toggled via `.env` configurations.
- **FR12 (Diagnostic Integrity):** Every audit session must document findings in `sandbox/notes.md` to maintain a historical "truth" of mission performance and tool reliability.
- **FR13 (Path Resilience):** Implementation of hierarchical `PROJECT_ROOT` resolution to ensure absolute path consistency across all diagnostic and production modules, preventing cross-environment directory corruption.

### 4.4 Graph Orchestration & Autonomous Operations
- **FR14: Persistent State:** The system utilizes **Google Cloud Spanner** to store network nodes, resident telemetry, and operational audit trails.
- **FR15: Relational Intelligence:** Implemented graph edges to map emergency lifelines and topological weights between residents and responders.
- **FR16: Transactional Integrity:** Level 3 dispatches use Spanner `run_in_transaction()` guarantees to prevent double assignments and ensure atomic updates.
- **FR17: Role Separation & Routing:** Strict separation between read-only `Risk_Analyst` telemetry checks and execution-bound `Mission_Operations` graph-based rescue routing.

## 5. Non-Functional Requirements (NFR)
- **Latency:** Inference for terrain risk analysis must be < 2 seconds.
- **Credit Awareness:** All LLM calls gated by idempotent checks to minimize API spend.
- **State Management:** ADK-based session management maintains context
- **Quota Awareness & Throughput:** The system implements "Cache-Before-Call" logic for geospatial assets and leverages high-throughput models like `Gemini 3.5 Flash-Lite` to maintain execution headroom under free-tier limits.
- **Sandbox Isolation:** The Sandbox environment must remain ephemeral; no persistent registry or database writes should occur within the sandbox during diagnostic runs.
- **Pipe Integrity:** Background telemetry redirected to `stderr` to preserve MCP JSON-RPC stream integrity.
- **Diagnostic Transparency:** All tool-calling errors in the sandbox must be captured as logs and, where possible, visual artifacts (screenshots/maps) for PRD compliance.
- **Edge Readiness:** Architecture maintains modularity to support future porting to Android 17 on-device AppFunctions using Gemma 4
- **Model Portability:** All Agentic Logic must be abstracted from the model backend to allow seamless switching between Cloud models and on-device Gemma variants via the `google-genai` interface.

## 6. Technical Validation: "The Mbagathi Truth"
- **Baseline:** Validated spatial reasoning for topographical analysis (`Gemma 4 (31B)` , `Gemini-2.5-Flash`, `Gemini-3.5-Flash`, `Gemini-3.5-Flash-Lite`).
- **Safe Ridge Logic:** The model autonomously identifies high-ground zones based on spectral terrain analysis (elevation vs. drainage).
- **MCP Diagnostics:** Validated tool-calling reliability via the MCP Inspector, ensuring our agents can "see" map assets locally even when cloud-disconnected.
- **Graph Verification:** Confirmed directed pathing from Sarah (Resident) at high-risk sump coordinates to Juma (Responder).
